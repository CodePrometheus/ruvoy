Ruvoy は Envoy の内部で動く Ruby アプリケーションランタイムです。Envoy が
HTTP を担い、Ruby が Rack を担い、その間を Rust の owned メッセージが橋渡し
します。

## ステータス

Ruvoy は現在 proof of concept です。データパス——リクエストのディスパッチ、
バックプレッシャー付きストリーミングレスポンス、キャンセル、アドミッション
制御——は実装済みでテストスクリプトに覆われており、下記の性能主張も事前
登録したプロトコルの下で測定したものです。ただし本番運用での実証はまだ
ありません。各プロセスは単一の Ruby 実行コンテキストのみを持ち、稼働中の
Envoy 内での設定リロードは未検証、長時間の soak テストも未実施です。
インターフェースは変更される可能性があります。

## 特徴

- **Envoy ネイティブの HTTP** — HTTP/1.1、HTTP/2、コネクション、タイム
  アウト、ダウンストリームのライフサイクルはすべて Envoy が管理します。
- **Rack アプリケーション** — 通常の `config.ru` を読み込み、Envoy の
  リクエストから構築された Rack 環境を受け取ります。
- **Fiber 並行性** — scheduler-aware な Ruby I/O が専用の CRuby オーナー
  スレッド上で交錯実行され、Envoy ワーカーが Ruby に入ることはありません。
- **Owned-data 境界** — スレッドを跨ぐのは Rust が所有するリクエストと
  レスポンスのみで、Ruby オブジェクトは決して跨ぎません。
- **ストリーミングレスポンス** — レスポンスボディはアプリケーションが
  生成するたびにチャンク単位で配信され、ダウンストリームのバックプレッ
  シャーはバッファリングではなく Ruby 側の生成側に直接かかります。
- **ストリーミングリクエスト** — ヘッダーが届いた時点でアプリケーション
  が呼ばれ、ボディは到着しながら読まれます。アプリケーションが追いつけない
  クライアントはバッファリングではなく減速させられます。
- **有界なアドミッション** — リクエスト数の予算により、超過分は Ruby に
  到達する前に拒否されます。
- **上流 HTTP ホップなし** — Rack 呼び出しに、別プロセスの Ruby アプリ
  ケーションサーバーへの loopback 接続は不要です。

## Ruvoy を使う場合と使わない場合

| | Ruvoy なし | Ruvoy あり |
|---|---|---|
| リクエスト経路 | Envoy → 上流 HTTP → Ruby サーバー | Envoy → Rust owned メッセージ → Ruby |
| Ruby のホスト | 独立したサーバープロセス | Envoy 内部の専用 CRuby オーナースレッド |
| プロトコルの受け渡し | リクエストは別の HTTP 接続にシリアライズされる | リクエストは owned データとしてワーカー境界を越える |
| I/O 並行性 | サーバーのスレッドまたはワーカー | Ruby オーナースレッド上の Async ファイバー |
| 障害境界 | Envoy と Ruby は別プロセス | Envoy と Ruby は同一プロセスを共有 |
| CPU バウンドな Ruby | 複数の Ruby ワーカーで複数コアを利用可能 | 単一の CRuby VM は GVL の制約を受けたまま |

Ruvoy は scheduler-aware な I/O と短時間の CPU-light な Rack 処理向けに
設計されています。CPU バウンドな Ruby を並列実行させるものではありません。

## アーキテクチャ

```text
client
  → Envoy worker
  → owned Rust request
  → CRuby owner thread
  → Async Fiber
  → owned Rust response
  → original Envoy worker
  → client
```

Envoy ワーカーが Ruby のハンドルを取得したり VM に入ったりすることはあり
ません。Ruby オーナースレッドが Rack アプリケーションを実行し、結果はダウン
ストリームの stream を所有するワーカーへコミットバックされます。

## 現在のスコープ

Ruvoy は Rack 環境を構築し、バイナリの `rack.input` を提供し、重複した
レスポンスヘッダーを保持し、列挙可能なレスポンスボディを消費し、ボディが
対応していれば `close` を呼び出します。

レスポンスボディはインクリメンタルにストリーミングされます。ヘッダーは一度
だけ送信され、アプリケーションが yield するたびに各チャンクが転送されるため、
ボディの完成前に最初のバイトがクライアントに到達します。遅いクライアントは
メモリに滞留させる代わりに Ruby 側の生成側へバックプレッシャーをかけ、切断
したクライアントは列挙を停止させてボディをクローズします。

リクエストボディも同様にストリーミングされます。ヘッダーが届いた時点で
アプリケーションが呼ばれ、`rack.input` を通してボディを到着しながら読むため、
アップロードと処理が重なります。アプリケーションがまだ読んでいない分は Envoy
に留まり、Envoy は空きができるまでクライアントからの読み取りを止めます。生
ソケットのハイジャック（`rack.hijack`）はサポートされず、コネクションは常に
Envoy に属します。

## スケーリング

各 Ruvoy プロセスはちょうど 1 つの CRuby VM を実行するため、1 プロセス内の
Ruby 処理は GVL により 1 コアに制限されます。スケールアウトはスレッドでは
なくプロセスを増やすことで行います。レプリカごとに 1 つの Ruvoy を実行し、
単一 VM の Ruby サーバーと同様に水平スケールします。

## ベンチマーク

### 環境

| コンポーネント | 構成 |
|---|---|
| マシン | 4 vCPU、32 GiB メモリ、x86_64 |
| システム | Linux |
| Envoy | `1.39.0`、concurrency `1` |
| Ruby | `4.0.5` |
| Rust | `1.97.1` |
| Rack | `3.2.6` |
| 負荷生成 | oha `1.15.0` |

### 混合ストレス

この実行ではアドミッション制御、回復、クライアントキャンセル、リソースの
安定性を検証しました。3 つの完全なサイクルで構成されます。

- 定常トラフィック：サイクルあたり HTTP/2 no-op リクエスト 45,000 件、
  200 ms 待機付き HTTP/1.1 リクエスト 6,000 件、256 KiB ボディ付き
  HTTP/1.1 リクエスト 1,200 件；
- リクエスト数の過負荷：15 秒間、最大 256 リクエストのみ受け入れ；
- 合計ボディの過負荷：15 秒間、受け入れボディ予算 64 MiB；
- クライアントキャンセル：意図的にキャンセルした 128 リクエスト；
- 回復：サイクルあたり no-op 20,000 件、待機リクエスト 2,000 件。

| 結果 | 値 |
|---|---:|
| 総リクエスト数 | `2,503,763` |
| HTTP 200 | `251,400` |
| 想定内の過負荷 HTTP 503 | `2,252,363` |
| トランスポートエラー | `0` |
| 定常・回復フェーズの失敗 | `0` |
| 制御リスナーの最大レイテンシ | `35.615 ms` |
| 各サイクル終了後のファイルディスクリプタ数 | `59` |
| Ruby live-heap の変化（回復サイクル 1 → 3） | `+2 slots` |
| ボディ過負荷中のピーク RSS | `489,332 KiB` |

定常および回復フェーズのリクエストはすべて HTTP 200 を返しました。HTTP 503
はすべて意図的な過負荷フェーズで発生したもので、拒否された仕事として報告
され、成功スループットには数えません。

この実行では負荷生成をサーバーと同一マシンで行い、サーバーはホスト CPU を
飽和させていません。したがってこの結果が支持するのはレジリエンスと有界な
過負荷の主張のみで、最大スループットの測定ではありません。

### サーバー比較

固定 commit 上で、Ruvoy、直接接続の Falcon `0.55.6`、直接接続の Puma
`7.2.0`、Envoy → Puma を、同一の Rack fixture で比較しました。

- oha はローカルネットワーク内の独立した 2 vCPU ホスト（RTT 約 0.03 ms）
  で実行し、負荷生成側がサーバーと CPU を奪い合うことはありません。
- 各測定は 10 秒のウォームアップと 30 秒の負荷で構成。セルごとに 7 ラウンド
  実施し、ラウンドごとにアーキテクチャの順序をローテーションします。
- すべてのリクエストが HTTP 200 を返し、トランスポートエラーがゼロの
  ラウンドのみを採用。報告値は中央値と相対標準偏差です。
- どのアーキテクチャも Ruby 実行コンテキストは 1 つだけ：Puma はシングル
  モードで 100 スレッド、Falcon は 1 インスタンス、Ruvoy はオーナースレッド
  1 本、Envoy は `concurrency 1`。
- 判定基準は実行前に固定：スループットと p99 の両方の改善が、5% と実測の
  ラウンド間変動のうち大きい方を超えた場合にのみ優位を主張できます。

No-op Rack アプリケーション、HTTP/1.1、100 コネクション、平文：

| サーバー | RPS 中央値（RSD） | p50 ms | p99 ms | CPU | RSS MiB |
|---|---:|---:|---:|---:|---:|
| Ruvoy | `31,270`（1.9%） | `3.06` | `5.01` | 189% | 94 |
| Falcon | `12,716`（0.5%） | `7.67` | `9.63` | 99% | 83 |
| Puma | `10,410`（5.5%） | `8.84` | `20.96` | 87% | 127 |
| Envoy → Puma | `9,754`（4.0%） | `9.92` | `17.63` | 159% | 185 |

同一ワークロードを TLS 1.3 で実行——Ruvoy と Envoy → Puma は Envoy が
終端し、Falcon と Puma はプロセス内で終端：

| サーバー | RPS 中央値（RSD） | p50 ms | p99 ms | CPU | RSS MiB |
|---|---:|---:|---:|---:|---:|
| Ruvoy | `32,065`（2.9%） | `2.98` | `4.85` | 192% | 95 |
| Falcon | `11,401`（3.0%） | `8.73` | `10.61` | 99% | 91 |
| Envoy → Puma | `9,674`（4.4%） | `9.97` | `17.44` | 162% | 191 |
| Puma | `8,728`（6.7%） | `9.87` | `25.52` | 87% | 148 |

アーキテクチャの差を分離できる比較対象は Falcon です。両者とも
fiber-per-request であり、違いはリクエストを loopback の HTTP ホップ経由
ではなく、同一プロセス内で owned データとして運ぶことだけです。Falcon に
対して Ruvoy は平文でスループット `+146%`・p99 `−48%`、TLS で `+181%`・
`−54%` を維持し、いずれも事前登録したノイズ閾値を超えています。
Envoy → Puma に対する差は `+221%` と `+231%` です。

正直に述べるべき 3 つの限定条件：

- No-op シナリオはリクエストあたりのフレームワークオーバーヘッドを測る
  ものであり、これらは上限値です。実アプリケーションの処理時間が長くなる
  ほど相対的な差は縮みます。100 コネクションで 200 ms の待機を模擬すると、
  4 つのサーバーはすべて同じ約 495 RPS の並行数上限に張り付きます。
- Ruvoy の CPU 列には、同一プロセス内で HTTP を処理する Envoy ワーカーが
  含まれます（約 1.9 コア、Falcon は約 1.0 コア）。コアあたりでは差は約
  `+29%` で、残りは Ruby スレッドにプロキシ級の HTTP フロントエンドを
  組み合わせたことによるものです。
- 1 MiB レスポンスのシナリオも実行しましたが、順位付けは成立しません
  でした。毎秒約 1,000 レスポンスを超えると 4 アーキテクチャすべてが
  ネットワーク経路のスループット上限に収束し、変動は 59–96% に達した
  ため、このシナリオが測っているのはリンクでありサーバーではありません。

測定は `scripts/run-benchmark.sh` によって生成されました。このスクリプトは
上記のプロトコル——リモート負荷生成、ローテーション、ウォームアップ、
ラウンドごとの検証、事前登録した判定——を強制し、各実行の生の oha 出力、
CPU・RSS サンプル、生成されたサマリーを保存します。
